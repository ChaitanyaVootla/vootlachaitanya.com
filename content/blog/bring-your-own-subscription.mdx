The AI runs on the subscription the user already pays for.

- They type in a chat dock **inside the app**. The agent answers there and builds dashboards on a canvas.
- The app's server never calls a model: no API key, no prompt, no harness, no bill.
- The catch: their agent has to be running, and they have to be technical enough to connect it.

## A plain MCP server is only half of it

Plenty of apps now ship an MCP server, so you can use them from Claude or ChatGPT. It works, but look at where you end up. You chat in the AI's window. The answers come back as text. When you want to see your actual data, you switch to the app, and the two never meet.

Bring the chat and the pictures into the app, over that same MCP connection, and it feels like an agent built into the site. The user never leaves the product. The only difference is whose agent it is, and who pays for it.

| | Build your own agent | Plain MCP server | MCP + dock and canvas |
| --- | --- | --- | --- |
| Where the user types | In your app | In their AI app | In your app |
| Where answers show up | In your app | In their AI app, as text | In your app, as chat and dashboards |
| Who pays for the model | You | Their subscription | Their subscription |
| Who builds the harness | You | Nobody | Nobody |
| Works with no agent connected | Yes | No | No |

The third column is the rest of this post. First, why I did not just build the first one.

## Three bills for one chat box

Adding an AI chat box to an app looks like a weekend of work. Then the invoice arrives, and with it a second job you never applied for: running an agent. When you put your own agent inside a product, you sign up for three things.

1. **The model bill.** Every question costs tokens, and the cost follows your most curious user, not your average one. For a side project that is the difference between free and a monthly surprise.
2. **The harness bill.** A chat box is the visible tenth. Behind it sit the prompt, the tool loop, retries, context limits, traces and evals. That is real engineering, and it never finishes, because every new model changes how the old prompt behaves.
3. **The second-best bill.** Your user already works with an agent all day. It has their preferences, their other tools and a harness built by a team much larger than yours. The one you bolt into your app starts from nothing and has to compete with it.

I build agent harnesses for a living, so I am not against writing one. I am against writing one where it adds nothing. For Kosh, which I use for my own holdings, and for Pramāṇa, a site for learning Indian history from its sources, an in-app agent would have added a bill and a worse brain.

Three pieces make that loop work.

### 1. A session the agent can join

In any tab, the dock's **New session** button shows a line to paste into the agent:

```text
Join my Kosh session ks_7Q2F4M3A (kosh MCP)
```

The agent calls `join_session` with that id. From then on the tab and the agent share a session: an ordered log of events that both sides read and write through the server. If a second agent joins, it takes the session over and the first one is told to stop. Each browser tab can hold its own session with its own agent.

### 2. A way for the agent to hear you

MCP is request and response. The agent asks, the server answers. Nothing in it lets my server tap the agent on the shoulder when the user types.

So the agent listens. `join_session` returns a small shell loop, and the agent runs it in the background. It is a long-poll against one URL, with a key that is good for that session only. This is the same loop, reformatted to read:

```sh
K='lk_…'   # per-session listen key, returned by join_session
while :; do
  out=$(curl -s --max-time 60 -H "Authorization: Bearer $K" -w ' %{http_code}' \
        'https://<your-app>/api/v1/agent/listen?wait=45')
  code=${out##* }; body=${out% *}
  case $code in
    200) printf '%s\n' "$body" ;;                        # a wake line: go read the events
    204) ;;                                              # nothing for 45 s: ask again
    410) echo 'session closed or taken over'; exit 0 ;;  # the only way out
    *)   sleep 15 ;;                                     # deploy, rate limit, network: retry
  esac
done
```

When the user sends a message, the open request returns one line:

```text
kosh ks_7Q2F4M3A #12 user: build me a defence board and highlight what I hold
```

That line is a nudge, not the message. The agent then calls `get_session_events` over MCP, which is the source of truth, and answers with `post_message`. Agents that cannot run a background command call a long-poll tool, `wait_for_session_events`, in a loop instead.

<Callout title="The dock never pretends">
The server knows when a poll is open, so the dock can be honest. It says **Listening** while one is open or ended under 75 seconds ago, and **Away · last seen 12 min ago** otherwise. A message sent while the agent is away is queued, and the dock says so. An AI feature that shows a spinner for work it cannot see is worse than one that admits nobody is home.
</Callout>

### 3. A canvas the agent builds without seeing it

The agent cannot see pixels, and I will not let it send HTML. So a canvas is **data**: a spec the agent writes from a fixed catalog of fourteen element kinds (charts, tables, KPI tiles, prose, stock cards, event feeds), laid out on a twelve-column grid. Data arrives by reference, never pasted in:

```ts
type DatasetSpec =
  | { kind: "tool"; tool: DashboardableToolName; args: Record<string, Value | ParamRef> }
  | { kind: "sql"; sql: string; limit?: number }      // read-only, and labelled as SQL
  | { kind: "inline"; columns: Column[]; rows: Row[]; source: Source } // labelled "Agent-supplied"
```

The first kind is the default. The agent names a tool and its arguments, and the server runs it **as the person viewing the canvas**. The numbers on screen come from the app, with the app's access rules and freshness labels. The model never retypes a figure, so it cannot get one wrong.

Three details matter more than they look:

- **Validation answers back.** Every path an element binds is checked against the tool's output schema. A wrong one comes back as `PATH_NOT_FOUND` with up to five nearest valid paths. A fraction displayed as a percentage is `FORMAT_UNIT_MISMATCH`, because a 100× display error in a finance app is a money error.
- **The agent gets a preview in words.** Each create or update returns one line per element, something like `table peers: 12 rows × 6 cols; pe 18.2..64.0; 2 nulls`. The agent finds its own empty panels before the user does.
- **Edits are operations, not rewrites.** `update_canvas` takes small ops (`upsert_element`, `move`, `remove_dataset`) against a revision. The user can drag a chart while the agent adds another, and neither wipes out the other's work.

## Same pattern, smaller: Pramāṇa

Pramāṇa uses the same shape with fewer parts. Its MCP server runs locally over stdio. You ask your question in Claude Code, and the answer, with its tables, charts, timelines and maps, appears live beside the page you are reading.

| | Kosh | Pramāṇa |
| --- | --- | --- |
| Where you type | A chat dock in the app | Your agent's own window |
| How the agent hears you | Long-poll on a per-session key | It doesn't need to: you are already talking to it |
| Where answers appear | Dock replies and canvases | A panel beside the page |
| Transport | Remote MCP over HTTP, API token | Local MCP over stdio |
| What the agent may change | Its own canvases and sessions | Nothing directly: every edit is a proposal a person approves |

If your users are happy typing in their agent's window, the Pramāṇa version is far less to build. The dock and the listening loop are what it costs to keep them inside your product.

## What you give up

This is not free. It moves the cost somewhere else.

- **The agent has to be running.** Close the terminal and nobody is listening. The dock says so, but it is still a worse experience than an agent that is always there.
- **Your users must be technical.** They need an MCP-capable client and the patience to paste a token. For Kosh that is a feature. For a consumer product it is a wall.
- **Clients disagree about everything.** I surveyed a dozen-plus MCP clients before building the connect screen. They differ on config paths, on whether they can send a static header, and on how they keep a secret. ChatGPT cannot send an API token at all, so it needs OAuth. I have built OAuth sign-in for Claude's apps, behind a flag that is still off, and ChatGPT is not covered yet.
- **Your tool list is now a cost.** When I last measured, Kosh's full list was 82 tools and about 449 KB as `tools/list` serves it. The server takes a `?toolsets=` parameter so an agent can ask for as few as 8 tools (about 46 KB).
- **You do not control the brain.** A different model, a different prompt, a user who told it to be terse. So nothing important may depend on the agent behaving. Scopes, rate limits, validation and labels are all enforced on the server. Kosh has no trading tools at all, and a test fails the build if one is ever imported.

## Whose subscription is it?

This is the question I would ask first, so here is the plain answer. Kosh never sees the user's AI account. There is no key for it on my server and no proxying of anyone's subscription. The user's own client, on their own machine, makes an outbound connection to Kosh with a Kosh token they created. To the model provider it is a person using their agent with a tool, which is what the agent is for. Terms differ by provider and by client, so read the ones for the client you plan to support before you build on this.

## When this fits

Use it when your users already live in an agent, when your app's value is its data and its views, and when the AI would otherwise be a cost you cannot recover. Developer tools, internal tools and personal software all fit.

Do not use it when the AI *is* the product, when it must work for someone who has never heard of MCP, or when it has to run while nobody is at the keyboard. That last one is a different problem, and it is why Cue, the system I build at work, has its own agents.

## Where the ideas came from

None of the parts are new, and I leaned on other people's work for each one.

- **Apps as MCP servers** is now common. [Lovable](https://docs.lovable.dev/features/agent-integrations) and [Base44](https://docs.base44.com/Integrations/app-mcp) both let a published app be driven from Claude or ChatGPT.
- **Long-polling for a human** over MCP has been done by several human-in-the-loop servers. Claude Code's Channels preview solves the same problem with push.
- **Flat, id-keyed UI specs** with patch operations come from A2UI and Grafana's dashboard schema. The text preview is the lesson I took from Grafana's assistant.

What I have not seen elsewhere is the combination: a chat dock and a canvas inside the app, driven by an agent the app neither runs nor pays for. If you have seen it, or built it, I would like to hear about it.

Kosh's repository is private for now. Pramāṇa is [open on GitHub](https://github.com/ChaitanyaVootla/pramana), and its design notes describe the proposal flow in full.
