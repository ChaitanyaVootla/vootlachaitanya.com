This post is a fixture. It never ships: `draft: true` keeps it out of every production build unless `BLOG_DRAFTS=1` is set. It exists so that each element a write-up can use is on one page, at a realistic length, in both themes.

The rest is written like a real post about agent harnesses, because layout problems only show up with real-looking text. Paragraphs should sit at a comfortable measure, around sixty-eight characters, with enough line height that a long technical argument does not feel like a wall.

## Why the harness is the product

Most agent demos are a model call with a nice prompt. Most agent _incidents_ are everything around it: a tool that returned half a page, a retry that ran twice, a trace nobody looked at. The harness is where that gets decided, so it is where most of the engineering goes.[^harness]

There are three things I want every run to answer:

1. What was the agent asked to do, exactly?
2. Which tools did it call, with which arguments, and what came back?
3. Did the result pass the checks we wrote down **before** the run?
   - If yes, ship it.
   - If no, keep the trace and turn it into an eval case.

And three things I try not to do:

- Let a tool return unbounded output into the context window.
- Retry a side-effecting call without an idempotency key.
- Judge a change by one good-looking run.

> If you can’t see the runs over time, you can’t tell anyone anything about the agent. You can only tell them about the demo.

### A tool contract, written down

A tool is a function with a schema, a budget and an owner. The contract below is the shape I keep coming back to. It is deliberately long, so the code block has to scroll inside itself on a phone instead of pushing the page sideways.

```ts
import { z } from "zod";

// One tool, described completely: what it takes, what it returns, what it may cost.
export const searchProtocols = defineTool({
  name: "search_protocols",
  description: "Full-text search over trial protocols the current user can read. Returns at most `limit` passages.",
  input: z.object({
    query: z.string().min(3).max(200),
    limit: z.number().int().min(1).max(20).default(8),
    studyId: z.string().regex(/^ST-\d{4}$/).optional(),
  }),
  output: z.array(
    z.object({ protocolId: z.string(), section: z.string(), passage: z.string().max(1200), score: z.number() }),
  ),
  budget: { timeoutMs: 4_000, maxCallsPerRun: 6, maxOutputTokens: 3_000 },
  sideEffects: "none",
  async run({ query, limit, studyId }, ctx) {
    const rows = await ctx.db.searchPassages({ query, limit, studyId, readableBy: ctx.user.id });
    ctx.trace.note("search_protocols", { query, hits: rows.length, studyId: studyId ?? null });
    return rows.map((row) => ({ ...row, passage: truncate(row.passage, 1200) }));
  },
});
```

### Reading the runs

Traces end up in Postgres, one row per step. This is the query I run most: the slowest tool calls in the last day, with how often they failed.

```sql
select
  tool_name,
  count(*)                                         as calls,
  percentile_cont(0.95) within group (order by duration_ms) as p95_ms,
  avg(case when status = 'error' then 1.0 else 0.0 end)     as error_rate
from run_steps
where kind = 'tool_call'
  and started_at > now() - interval '1 day'
group by tool_name
having count(*) > 20
order by p95_ms desc
limit 10;
```

## Comparing harness choices

A table wider than the reading column. On a narrow screen it should scroll inside its own box.

| Concern              | Bare SDK calls                 | Framework graph (LangGraph)          | Hosted agent platform          |
| -------------------- | ------------------------------ | ------------------------------------ | ------------------------------ |
| Control over prompts | Total                          | Total                                | Partial                        |
| Retries and timeouts | You write them                 | Per node, declarative                | Built in, opaque               |
| Traces               | You build them                 | Built in, exportable                 | Built in, vendor format        |
| Evals                | Separate harness               | Separate harness, easy to wire       | Sometimes built in             |
| Lock-in              | None                           | Low                                  | High                           |
